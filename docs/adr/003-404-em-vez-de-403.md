# ADR 003 — Recurso de outro tenant devolve 404, não 403

**Status:** aceita · **Data:** 2026-08 (Fase 1)

## Contexto

Um usuário da organização A pede `/api/funcionarios/{id}` com um id da organização B. O
acesso precisa ser negado. Falta escolher **como** negar.

## Decisão

**404 Not Found.** Do ponto de vista daquele usuário, o recurso não existe — e é
literalmente verdade: sob o filtro global, aquela linha não está no conjunto que ele
consulta.

Na prática, isso cai de graça: o endpoint resolve o recurso **através** do filtro, e um id
de fora simplesmente não é encontrado. Não há conferência manual depois — porque é a
conferência manual que se esquece.

## O que foi recusado

**403 Forbidden.** É o código semanticamente óbvio, e é o errado aqui.

Um 403 diz *"este id existe, e você não pode vê-lo"*. Um 404 diz *"não há nada aqui"*. A
diferença entre as duas respostas é um **oráculo**: com ela, um atacante enumera
identificadores e descobre quais existem no sistema inteiro, um por vez, sem nunca ler um
único dado. Isso mapeia o vizinho.

O mesmo raciocínio aparece no login, por outro caminho: a resposta é idêntica para e-mail
malformado, inexistente e senha errada — e o **tempo** de resposta também é, porque um
hash falso é conferido quando o usuário não existe. Diferença observável é informação.

## Consequências

**Boas:** não há oráculo de existência em rota nenhuma. `VarreduraIdorTestes` percorre
todas as rotas `{id:guid}` exigindo 404 ou 400, e rota nova entra na varredura sozinha.

**Ruins:** o diagnóstico fica pior. Um desenvolvedor vendo 404 não sabe se errou o id ou se
o recurso é de outro tenant. Aceitável: quem depura tem o log e o banco; quem ataca não.

**Cuidado permanente:** um 403 legítimo — perfil sem permissão para aquela **operação** —
continua existindo e é correto. A distinção é entre *"você não pode fazer isto"* (403) e
*"isto não existe para você"* (404).
